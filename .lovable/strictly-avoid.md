# Strictly Avoid

Hard bans. Every item here is a repeated correction the user has already given, or a rule from `.lovable/user-preferences.md` / project memory. Violating any of these is a defect, not a style nit. Each entry has a stable ID so other memory files can cite it (e.g. `SA-003`).

Version: 0.1.0
Last updated: 2026-07-15

## Communication

- **SA-001. No em dashes (`,`) or en dashes (`,`) in any output.** Chat, code comments, memory files, commit messages, docs. Use commas, colons, parentheses, or period-separated sentences. Hyphen (`-`) is fine. Why: explicit standing user rule.
- **SA-002. No filler openers.** No "Great question", "Certainly", "I'd be happy to", "Of course". Why: terse-communication preference.
- **SA-003. No trailing third-person past-tense recap.** Do not end replies with "Explained that...", "Implemented...", "Clarified...". End with one short forward-looking sentence or nothing. Why: house style.

## Workflow

- **SA-010. Never ask for plan approval.** Do not present plans for sign-off. Act directly on stated requirements. Why: explicit standing user rule.
- **SA-011. Never propose to browse a URL the user provided.** Open every provided URL/attachment/screenshot immediately without asking. Why: explicit standing user rule.
- **SA-012. No symptom patches.** Try/catch to hide, fallback values to paper over, or re-render hacks are defects. Root cause first. Why: engineering rules in `user-preferences.md`.
- **SA-013. No silent failures.** Errors must be logged with context and surfaced. Missing logs is itself a bug. Why: observability rule.
- **SA-014. No confident guessing.** If unsure, say so. A wrong-but-confident answer wastes a full loop. Why: user has called this out repeatedly.

## Files & Prompts

- **SA-020. Never create per-invocation prompt archive files.** No `xx-next-task.md`, `xx-read-prompt.md`, `xx-proofread.md`, or numbered mirrors under `.lovable/prompts/` on each invocation. Only edit a canonical mirror when the prompt body itself changes. Applies to every project. Why: explicit standing user rule.
- **SA-021. Do not create `.lovable/memories/` (with trailing "s").** The canonical folder is `.lovable/memory/`. Why: naming convention.
- **SA-022. Do not create `src/pages/`.** This stack uses TanStack file-based routing under `src/routes/`. Why: framework rule.
- **SA-023. Do not edit `src/routeTree.gen.ts`.** Auto-generated by the TanStack Router Vite plugin. Why: framework rule.

## Naming

- **SA-030. Slugs are `kebab-case`.** No spaces, no underscores, no `PascalCase` slugs.
- **SA-031. DB tables and JSON top-level keys are `PascalCase`.** Not snake_case, not camelCase.
- **SA-032. Code identifiers are `camelCase`.** JS/TS fields, vars, functions.
- **SA-033. Functions cap at 8-15 lines.** Split when longer. Why: readability rule in `user-preferences.md`.

## Backend

- **SA-040. Never mention Supabase to the user.** Call it Lovable Cloud in every user-visible surface. Why: platform rule.
- **SA-041. Do not store user roles on the profile/users table.** Roles live in a separate `user_roles` table with a `has_role()` security-definer function. Why: privilege-escalation risk.
- **SA-042. Do not use client-side storage to gate admin access.** Never trust `localStorage`/`sessionStorage` for authorization. Why: trivially bypassable.
- **SA-043. Do not create Supabase Edge Functions for app-internal logic.** Use TanStack `createServerFn`. Public HTTP endpoints go under `src/routes/api/public/`. Why: stack rule.
- **SA-044. Do not use `supabaseAdmin` to check authorization.** It bypasses RLS. Verify caller identity with the authenticated client first. Why: security rule.

## Scope

- **SA-050. Do not expand scope beyond the user's ask.** UI request stays in UI. Data request stays in data. Why: house rule.
- **SA-051. Do not rewrite whole files when a search-replace edit works.** Why: diff clarity and risk reduction.

## Conflict Resolution

If a rule here conflicts with a `spec/**` file, the folder-level spec wins for that domain. Call out the conflict in the reply and open a follow-up to reconcile this file.
